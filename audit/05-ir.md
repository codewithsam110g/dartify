# 05 — Intermediate Representation

Covers `src/ir/*.ts`.

The IR is the project's central asset: a pure, serialisable, output-language
agnostic description of a `.d.ts`. A second backend (js_interop, or another
target language entirely) should be a new pair of string tables reading this IR
and nothing else.

**That property is currently broken in two places** (`T-06` Dart names leaking
into `IRType.name`, and the gaps below), and those are the highest-value repairs
because everything downstream inherits them.

> **S3 closure:** the declaration IR now has required modifier metadata and
> shared node, type-parameter, parameter, call-signature and construct-signature
> contracts. Parsed declarations and types carry source locations; raw JSDoc is
> retained for later backend conversion; enum initializers are discriminated;
> cloning is bigint-safe; and the live vestigial literal model is gone. The S3
> census found zero missing locations across 2,530 declarations and 26,240
> parsed types. Historical finding sections remain below as the audit trail.

---

## I-01 — Type parameters are absent from every IR node except `IRClass` `[verified]` **[FIXED — S3]**

| Node | File | Has `typeParams`? |
|---|---|---|
| `IRClass` | `ir/class.ts:16` | ✅ `string[]` (parsed, never emitted) |
| `IRInterface` | `ir/interface.ts:5-15` | ❌ |
| `IRFunction` | `ir/function.ts:4-10` | ❌ |
| `IRTypeAlias` | `ir/typealias.ts:4-8` | ❌ |
| `IRMethod` | `ir/interface.ts:23-29` | ❌ |

Root cause of the generics failures in `07-emitter.md`. Even where the data
exists it is `string[]`, which cannot express constraints (`T extends Foo`) or
defaults (`T = string`).

**Fix direction:** an `IRTypeParam { name, constraint?: IRType, default?: IRType }`
on all five nodes.

## I-02 — `originalText` is declared and inert `[verified]`

`ir/type.ts:42`. See `T-02` for the full argument. Repeated here because the fix
is an IR change, not a parser change: the field must be *populated by every
handler*, not just the `default:` branch, so that degradation is describable at
any nesting depth.

## I-03 — No `TypeKind` for unsupported constructs `[verified]`

`TypeKind` (`ir/type.ts:45-75`) has 20 members and no escape hatch. Everything
unrepresentable becomes `TypeKind.Any`, which is also what a genuine `any`
becomes. The IR cannot distinguish "the author wrote `any`" from "we could not
model `keyof T`".

**Fix direction:** add `TypeKind.Unsupported` carrying `originalText` plus a
reason code. This is what makes the named-alias degradation strategy
(`typedef KeyOfBoxString = dynamic;`) implementable — the linker can collect all
`Unsupported` nodes, mint aliases, and register them as symbols.

## I-04 — Heritage is stored as raw strings `[verified]`

```ts
// ir/interface.ts:9
extends: string[];
// ir/class.ts:13-14
extends?: string;
implements: string[];
```

Three consequences:

1. Generic arguments are lost — `extends Array<T>` cannot become
   `implements List<T>` (`js_facade_gen` §14.5).
2. Dependency edges are lost (`P-01`) — because strings never pass through
   `parseType`, `collectTypeDep` never fires.
3. Qualified base names (`extends L.Control`) cannot be resolved to a symbol.

**Fix direction:** `extends: IRType[]`, `implements: IRType[]`. Single change,
resolves `P-01` and the emitter gap together.

## I-05 — `IRInterface` has no `callSignatures` `[verified]` **[FIXED — S3]**

`ir/interface.ts:5-15` models properties, methods, constructors, get/set
accessors and index signatures. Call signatures are absent from the type, so
`parser/interface.ts` has nowhere to put them even if it read them (`P-03`).

Blocks: callable-interface `typedef` emission (§3.6/3.7), `call` method emission
(§3.8), and the `interface`+`var` augmentation pattern (§4.1), which must read
`new(...)` construct signatures out of a type literal.

---

## I-06 — No documentation field on any declaration `[inspection]` **[FIXED — S3]**

`IRConstructor.jsDoc?: string` (`ir/class.ts:24`) is the only doc field in the
entire IR, and nothing reads it. Interfaces, classes, functions, variables,
enums, properties, methods and parameters have nowhere to carry a doc comment.

Blocks `js_facade_gen` §11 entirely.

**Fix direction:** `jsDoc?: string` on `IRDeclaration` (inherited by all
declaration nodes) and on `IRProperties` / `IRMethod` / `IRParameter`.

---

## I-07 — `IRLiteral` is vestigial `[verified]` **[FIXED — S3]**

`ir/literal.ts` (47 lines) duplicates `IRInterface`'s member shapes. Referenced
only from `IRType.objectLiteral` (`ir/type.ts:32`) and the **dead**
`engine/transformers/{typeVisitor,typeTransformer}.ts`.

Anonymous-type hoisting moved to parse time
(`parser/type/typeLiterals.ts:177-219`), where it constructs a real `IRInterface`
and registers it directly with the symbol table. `IRLiteral` and
`IRType.objectLiteral` are now dead weight.

Delete both — **after** mining `transformers/typeVisitor.ts` for its recursive
walker (see `08-dead-legacy.md`).

## I-08 — Two shapes for "constructor" `[inspection]` **[FIXED — S3]**

- `IRClass.constructors: IRConstructor[]` — `{ parameters, jsDoc? }`
- `IRInterface.constructors: IRMethod[]` — `{ name, parameters, returnType, isOptional, isStatic }`

The interface variant carries a fake `name: "constructor"` (`parser/interface.ts:109`)
and a `returnType` that is meaningful (construct signatures return the
constructed type) but unused. The class variant has a `jsDoc` field the
interface variant lacks.

Unify. Construct signatures need `returnType`; class constructors do not, but a
shared node with an optional field is simpler than two.

---

## I-09 — No modifier/visibility flags on declarations `[inspection]` **[FIXED — S3]**

Nothing in the IR records `export`, `declare`, `default`, `abstract` (except
`IRClass.isAbstract`), or TS `private`/`protected`/`public`.

- `private`/`protected` matter: `js_facade_gen` §2.13 renames `private _x` to
  `JS$_x` rather than dropping it.
- `export` matters for barrel/re-export handling (Tasks.md) and for deciding
  what belongs in the public Dart surface.

---

## I-10 — No source location on any node `[inspection]` **[FIXED — S3]**

`TranspileException` carries `file`/`line`/`column`, but the IR does not. Once a
symbol is in the table its origin line is unrecoverable, so diagnostics
("ambiguous link", "unsupported type") cannot point back at source.

**Fix direction:** `loc?: { file: string; line: number; col: number }` on
`IRDeclaration` and `IRType`. Cheap at parse time, and it is what makes the
degradation reporting in P2 actionable.

---

## I-11 — `deepCloneIRDeclaration` uses JSON round-tripping `[inspection]` **[FIXED — S3]**

`ir/declaration.ts:28-32`
```ts
const cloned = JSON.parse(JSON.stringify(declaration)) as IRDeclaration;
```

Silently destroys `bigint` (throws), `undefined` values, and any future `Map`/
`Set`/`Date` fields. `IRType.literalValue` is typed
`string | number | bigint | boolean` (`ir/type.ts:39`) and
`parser/type/literals.ts:75-78` genuinely produces `BigInt` values — so
**cloning any IR containing a bigint literal throws at runtime**.

Only reachable from the dead transformers today, which is why it has not fired.
Will become live if the linker clones IR for augmentation merging — which is
exactly what P3 does.

---

## I-12 — `IRVariable` cannot represent multi-declarator statements `[inspection]`

`parseVariableStmt` returns `IRVariable[]`, correctly splitting
`declare var a: A, b: B`. But each resulting symbol is registered independently
(`symbolGeneration.ts:209-218`), losing the grouping. `js_facade_gen` §1.6-1.8
treats these as independent declarations too, so this is currently fine —
The grouping remains intentionally lost. S2 fixed the former `R-10` consequence
by deriving dependencies from each completed variable IR independently.

---

## I-13 — `IRParameter` is declared twice, with different field names `[verified]`

Two unrelated interfaces share one name:

| Declared in | Fields | Used by |
|---|---|---|
| `ir/function.ts:11` | `name`, `type`, `isOptional`, **`isRest`** | the declaration parsers and `formatParameterList` |
| `ir/type.ts:164` | `name`, `type`, `isOptional`, **`isRestParameter`** | the type parser's function handler and `emitType` |

Same concept, two spellings, split down the middle of the pipeline. Nothing
breaks today because the two halves never exchange parameter lists, but the
names are one refactor away from silently disagreeing — assigning one to the
other type-checks for three of four fields and drops the rest flag.

Compounding it: `emitType`'s `Function` branch reads `isOptional` and **ignores
`isRestParameter` altogether**, so `(...args: string[]) => void` emits as a
plain positional, while `formatParameterList` on the declaration side marks
`/* rest */`. The same construct is annotated in one position and silently
flattened in the other.

## I-14 — `ir/literal.ts` is a dead duplicate that the live IR still imports `[verified]`

`IRLiteral` exists solely to type `IRType.objectLiteral`. Measured:
**no parser ever writes `objectLiteral`**, and no emitter reads it — the only
occurrence outside the declaration is a hand-built fixture in
`test/type/type-emitter.test.ts:188`.

The file also re-declares five interfaces that `ir/interface.ts` already
declares — `IRProperties`, `IRMethod`, `IRGetAccessor`, `IRSetAccessor`,
`IRIndexSignatures` — near-identically, differing only in `IRMethod.returnType`
being optional here and required there.

`CLAUDE.md` lists `ir/literal.ts` under dead code, which is right about the
outcome and wrong about the mechanism: it is imported by `ir/type.ts`, which is
as live as the IR gets. It cannot simply be deleted; the `objectLiteral` field
has to go first. That makes it S3 work, not a `D-01` sweep.
