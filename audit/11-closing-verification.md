## New findings

### CA-32 — A lone CR in JSDoc escapes the `///` comment and injects Dart declarations

> The separate codex release audit found the same defect independently as
> `DAR-022` (`10-release-17e8aa9/`); see `12-MASTER-REPORT.md`.

- **Severity:** medium · **Confidence:** confirmed · **Category:** security / implementation
- **Location:** `src/engine/emitter/packagejs/text.ts:84` (`dartDocLines` splits on `/\r?\n/`)
- **Evidence:** `10-closing-17e8aa9/fixtures/backend/lonecr/lonecr.d.ts`
  (`/**\r * Harmless summary.\r external void injected();\r */`) generates a
  `///` line containing a raw `\r`. The Dart scanner ends the comment at the CR,
  so `external void injected();` becomes a top-level declaration. Probe:
  `import 'package:cr/lonecr.dart'; void main() { injected(); }` produces no
  `dart analyze` issues, and `dart compile js` succeeds with a call to
  `injected()` in the output. Any Dart text fits the same slot (declarations,
  non-external functions with bodies, top-level initialisers).
- **Consequence:** documentation text in third-party `.d.ts` input becomes
  generated code while the output stays analyzer-clean. This is stronger than
  `CA-12` (which rewrites text); here input controls arbitrary declarations.
- **Remediation:** split doc text on every line terminator Dart and
  JavaScript recognise (`\r\n`, `\n`, `\r`, and U+2028/U+2029 for safety)
  before prefixing `///`, and add the `lonecr` fixture as a regression test
  that asserts no generated line lacks its `///` prefix.

### CA-33 — The closing audit's registration corrupted `audit/FINDINGS.md`

- **Severity:** low · **Confidence:** confirmed · **Category:** intent (registry integrity)
- **Location:** `audit/FINDINGS.md` (introduced by `c8b0eff`, extended by `652caf1`)
- **Evidence:** the `CA-11` row breaks after "File names containing `'` or ",
  and the file's own header (`# Consolidated Findings` through the end of
  "Found during the pre-S5 barrier, S5 and S6") is spliced in. Then the row resumes
  (" produce invalid Dart import/export directives …") and the remaining CA rows
  follow. The title contains `` $` ``, which `String.prototype.replace`
  expands to "the text before the match", so the registration step pasted
  everything before the insertion point into the row. Every pre-CA finding row
  therefore appears twice; `X-16` occurs 2 times at `17e8aa9` and 4 times now.
  Separately, `CA-30` and `CA-31` were appended after the final baseline table
  (lines 565-566) with no table header, so they don't render as registry rows.
- **Consequence:** the registry `CLAUDE.md` tells every session to "read first"
  has a broken row and a duplicated index, and `CA-22`'s line citations
  (`:107`, `:183`) no longer identify unique rows.
- **Remediation:** delete the spliced copy, rejoin the `CA-11` row, move
  `CA-30`/`CA-31` (and `CA-32`/`CA-33`) into the closing-audit table, and
  register future rows with a replacement *function* (or `split`/`join`) so
  `$` sequences in titles are literal.
