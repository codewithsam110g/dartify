# Architecture

*Decisions: D-05, D-06, D-08–D-16, D-19–D-26. This page describes the system as it is meant to be; where the code
differs, that is a bug or a pending decision, and it is listed at the bottom.*

## Purpose and scope

dartify (npm: `dart_bindgen`) generates Dart JS-interop bindings from TypeScript `.d.ts` declaration files, built on
`ts-morph`. v1 is a drop-in replacement for the archived `dart-lang/js_facade_gen`, targeting `package:js` (D-05); v2
adds a `dart:js_interop` backend behind a CLI flag (D-06).

**Why it exists (D-15).** The author maintains **uber/h3**'s Dart bindings (they did the v3→v4 upgrade; it was their
first FOSS contribution and made them an official h3 maintainer). h3's **web** support was generated by
`js_facade_gen`, which is archived, tells you not to use it, and is still load-bearing for h3 and many other
`package:js` packages. dartify replaces the tool the author's own project depends on, so `def_files/h3/h3.d.ts` is
the real consumer, not a demo, and h3 is the first adopter. h3 is also exactly a codebase whose `package:js`
dependency extends past the generated bindings, which independently confirms the `package:js` v1 target. Public
positioning should say it: "written by an h3 maintainer to replace the archived tool h3 itself depends on".

**What it is not.** Not a general TypeScript compiler: the input contract is declaration files (D-08) — no
function-body, statement, implementation-inference or expression lowering. Not a `dart:js_interop` migration tool in
v1 (D-05).

The `package:js` backend's policies (constructors, overrides, default type arguments, degradations, imports,
`Promise`) are recorded in the S5 section of [history/plan-s0-s6.md](history/plan-s0-s6.md); the semantic contract is

A v2 backend is a second `Backend` beside `packagejs/` — "a pair of string tables (one type emitter, one statement
emitter), not a second compiler" (D-06). The same seam admits other target languages.

## Data and control flow

```
cli.ts → transpiler.ts
           ├ PHASE 1  phase/symbolGeneration.ts  → parser/* → IR → SymbolTable
           ├ PHASE 2  semantic/* + linkerPhase.ts → canonicalizes/merges/names,
           │                                        mints aliases, links dep graph
           └ PHASE 3  phase/emitterPhase.ts      → Backend (emitter/backend.ts)
                                                     → emitter/packagejs/* → .dart
```

1. **Generation** parses each declaration into IR with full metadata and signatures; anything not captured here is
   unrecoverable (D-11). The parser is otherwise syntax-only, but the type checker is available and cheap — use it
   before declaring a construct unrepresentable (finding `T-14`: `typeof x` was written off from syntax and turned out
   87% resolvable; checking all 449 three.js `typeof` nodes cost ~60 ms).
2. **Semantic + link** merges declarations, names everything legally and deterministically, mints named degradations
   (D-10), and links each IR use site to a checker target. There is no fuzzy wrong-file/name fallback: missing modules
   are visible edges.
3. **Emission** renders each library, then plans imports and support typedefs, then resolves barrels. Errors per
   declaration are contained and visible (D-26).

**Watch** (`dartify -w`) re-runs the same phases against cached per-file / per-statement results and re-renders only
libraries whose fingerprints changed; the contract is differential (D-16).

## Invariants

- Incremental output equals a cold build byte for byte (D-16) — `test/watch-differential.test.ts`, `pnpm test:incremental`.
- Every unrepresentable type is a named, documented typedef; no use site emits bare `dynamic` (D-10) — `test/type/`,
  S5 fixture golden.
- Generated output for h3, Leaflet, all 420 three.js libraries, the S5 fixture, synthetic/legacy fixtures and all 90
  conformance cases matches the exact analyzer census (D-14) — `pnpm test:dart`.
- Generated bindings behave like the JavaScript library under dart2js (D-14) — runtime probe, `pnpm test:e2e`.
- No `// ERROR emitting` markers or returned errors on the 1,654-file corpus (D-26) — `pnpm test:stress`.
- h3 reproduces all 63 golden declarations (D-15) — `test/conformance/h3-golden.test.ts`.
- `tools/` and `@viz-js/viz` stay out of the shipped bundle (D-13).
- No process-global compiler state (D-20).

## Known gaps

The open findings of the v1 release audits (48 verified defects: 3 high, 26 medium, 19 low) and the pre-D3 open
findings are tracked in the hardening register, [hardening/findings.md](hardening/findings.md), and fixed by the
hardening gate before the `1.0.0` publish (D-30). The largest clusters: module/export identity, input-boundary
reporting, name and text legality after allocation, type and class fidelity, incremental state, and tooling/CI/docs.

Planned beyond v1: checker evaluation of utility and mapped types (`Record`, `Omit`, `Pick`) so named fallbacks can
resolve to precise shapes; emitting external-module augmentations (modeled and visibly suppressed today).
