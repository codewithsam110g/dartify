IDs are `HD-NN`, append-only, same rules as [../decisions.md](../decisions.md). A decision proposed but not yet agreed lives in
[pending.md](pending.md) under the number it will keep.

findings named in it; the brief that fixes them implements the decision and may not reopen it without a superseding HD.

| HD-13 | *Refined by HD-16.* **Supersedes HD-03. Syntax errors follow the all-or-nothing write rule** (`DAR-001`, `CA-10`): TypeScript **syntactic** diagnostics of every file dartify parses for symbols (inputs and the dependency files it generates from) are generation failures — each reported with `file:line:column` and its `TSnnnn` code, **nothing is written**, and the run exits 1, exactly like every other generation failure (task 4.11, `src/transpiler.ts` `transpile()`; watch mode already writes nothing on failure). Recovery output never reaches disk. Type-check (semantic) diagnostics stay non-fatal: unresolved names degrade to named typedefs (D-10) and are reported by the link report. | 2026-11-05 | D-09, D-10 |
| HD-14 | *Refined by HD-15.* **js_facade_gen invocation mapping** (the planner's choice under HD-07, `CA-30`): positional arguments are input files/globs, equivalent to `-d`; `--destination` is an alias of `-o`; `--base-path` overrides the input root that output paths are relative to (every input must lie under it, else an error); with positional inputs and no `-o`/`--destination`, a run that yields exactly one library prints it to stdout (logs to stderr), as js_facade_gen's basic usage did, and a multi-library result is an error asking for `--destination`. `--skip-formatting` is accepted as a no-op (dartify never runs a formatter). `--generate-html`, `--rename-conflicting-types`, `--explicit-static` and `--trust-js-types` exit 1 with a message stating what dartify does instead. Unknown flags are rejected (`yargs` strict mode). Without positional inputs, today's behaviour (`-o` default `./dart_out`) is unchanged. | 2026-11-05 | D-31 |
| HD-15 | **Refines HD-14: CLI details settled in HG-2** (agreed 2026-11-06). `--watch` in stdout mode (positional inputs, no `-o`/`--destination`) is a usage error asking for `-o`/`--destination`: a rebuild loop cannot print one library, and silently writing `./dart_out` would hide where output went. Giving the output directory (`-o`/`--output`/`--destination`) or `--base-path` more than once is a usage error, not a silent pick. A leading `!` makes an argument a negation glob, so `-d "**/*.d.ts" -d "!x.d.ts"` works. Each refused js_facade_gen flag's one-line message states what dartify does, read off the code (`src/cliOptions.ts`). Other output collisions among `.d.ts`/`.d.mts`/`.d.cts` inputs stay errors (HD-04); the `.d.mts`+`.d.cts`-without-`.d.ts` case is tracked as risk `RS-01` in [../issues.md](../issues.md). | 2026-11-06 | HD-04, HD-14 |
| HD-16 | **Refines HD-13: scope and reporting of syntax failures** (agreed 2026-11-06). Dependency declaration files dartify generates from, including typings under `node_modules`, are in scope: a syntax error there fails the run like one in an input. Accepted trade-off: typings written in syntax newer than the TypeScript bundled with ts-morph stop the run where they were silently accepted before (risk `RS-02`, mitigated by keeping ts-morph current; h3-js, leaflet and three parse cleanly). A failing build prints every failure (`TranspileException.diagnostics` carries them all) and only the failures: its link and emission counts describe a recovered program, so they are not printed, in one-shot and watch mode alike. | 2026-11-06 | HD-13, D-10 |
| HD-17 | *Refined by HD-21.* **Runtime dispatch follows module exports** (`DAR-003`; agreed 2026-11-06 at the HG-3 brief). With a root — `--js-root R`, or `export as namespace R` (UMD) — a value's JavaScript path is `R.` plus the property path under which an **input file** exports it, following the export graph: `export *`, `export { a as b }` with or without `from`, a declaration imported and then exported (`import { A } from "./a"; export { A }`), `export { default as X }`, and `export * as ns` (which adds `ns.` to the path). A default export of the input file itself binds `R.default`. `export = x` makes `x` the root itself: a namespace merged with `x` binds its members as `R.member`, not `R.x.member` (the lodash shape a naive fix gets wrong). A value reachable by several routes takes the first in a deterministic order (they all denote one JavaScript object). Several input files: their exports are combined, and two different values at one path are a counted diagnostic. A value with **no runtime export route** from an input (an internal class) keeps `R.<local name>` with a counted diagnostic — not dropped, because dropping it would also remove a type other declarations use. **Without a root, nothing changes**: module declarations bind bare globals, as in js_facade_gen (D-31). Why: three.js re-exports 162 default exports by name (`export { default as ConstNode } from "./ConstNode.js"`), so the naive "`export default` → `R.default`" fix would break it; the path must be the name the entry exports. Proof is runtime, not analyzer (D-14): the runtime probe grows these cases. | 2026-11-06 | D-09, D-14, D-31 |
| HD-18 | **Public names in Dart follow the TypeScript export names** (`CA-03`, `DAR-004`; agreed 2026-11-06). Dart cannot rename on export, so: a declaration exported **only** under an alias (`declare function hidden(): void; export { hidden as publicName }`) is emitted directly as `publicName` — no typedef needed. An **additional** public name is a `typedef B<T> = A<T>;` (type parameters and bounds kept) for classes, interfaces, enums and type aliases — Dart 3 allows constructors and static members through a class typedef — and, for functions and variables, a second `external` binding with the correct `@JS` path (no tear-off of an external function: tear-offs are fragile with `package:js` interop). Named re-exports resolve through barrel chains (`export { A } from "./b"` where `b` only `export *`s `a`) and through import-then-export to the real declaration. `export { default as X }` gives `X`; a bare `default` export name keeps the local declaration name (Dart has no `default` identifier). Consumers of a barrel see the TypeScript public names, not the internal ones. | 2026-11-06 | D-09, D-11, D-31 |
| HD-19 | **`export * as ns from "./m"` points to Dart's own idiom** (`CA-03`, `DAR-004`; agreed 2026-11-06). In Dart the namespace is written by the consumer: `import 'm.dart' as ns;` gives exactly `ns.foo()` **and** `ns.Widget` with full types. A generated forwarding class was rejected: it could carry functions and variables but never types (Dart has no nested types), so users would get `ns.foo()` from the barrel yet still have to import `m.dart` to write `ns.Widget` — half an API, and inconsistent. So: the barrel does not re-export `ns`; it carries the comment `// export * as ns from './m': import 'm.dart' as ns;`; `m.dart` is **always emitted**, even when `ns` is its only route (today it can go missing); a counted diagnostic gives the same import line; dispatch stays correct (`R.ns.<name>` under a root, HD-17). | 2026-11-06 | D-09, HD-17 |
| HD-20 | **Refines HD-05: what an ambient module without a root binds** (`CA-06`; agreed 2026-11-06). HD-05 forbids an invalid `@JS` path but did not say what to emit instead. For `declare module "<specifier>" { … }`: with `--js-root`, the same export-following rule as module files (HD-17). Without a root and with a specifier that **is** a valid JavaScript property path (e.g. `h3`), keep `<specifier>.<name>` as today — h3 depends on it. Without a root and with a specifier that is **not** one (`@scope/pkg`, `pkg/sub`, `my-lib`), bind the module's values as **bare globals**, exactly as module files without a root already do, plus a counted diagnostic suggesting `--js-root`: bindings that compile and are consistent with module files. The alternative, skipping those values, was rejected: it loses bindings for no gain. | 2026-11-06 | HD-05, HD-17, D-31 |
| HD-21 | **Refines HD-17: `EXPORT_ROUTE_MISSING` is reported once per Dart library** (agreed 2026-11-06 at the HG-3 Phase A review). One diagnostic per library names every declaration in it that no input exports at runtime (each still binds `R.<local name>`), instead of one diagnostic per declaration. Why: under `--js-root THREE`, `Three.Core.d.ts` leaves 740 declarations unexported (610 in `nodes/`, which only the WebGPU entry exports); per-declaration reporting made `-lv` 740 lines long without telling the user more. Nothing is hidden: every name is still listed, and the default output's `Emission:` count stays a count of diagnostics. | 2026-11-06 | HD-17, D-09 |
| HD-22 | **Augmenting a browser/lib type becomes a typed Dart extension on the SDK type** (issue `I-01`, found in HG-3 Phase A; agreed 2026-11-06). When a global declaration merges with a TypeScript default-lib declaration that dartify maps to a Dart SDK type (`browserTypes.ts`, D-22) — `interface Window { myProp: string }` in a script file or in `declare global { … }` — dartify no longer emits a standalone anonymous class of that name (which silently shadowed `dart:html`'s `Window` in that library). It emits an extension on the SDK type in the declaring library, e.g. `extension WindowAugment on Window { String get myProp => js_util.getProperty(this, 'myProp'); … }`: getters via `js_util.getProperty`, setters via `js_util.setProperty` (not for `readonly`), methods via `js_util.callMethod`, with the same type lowering and degradations as every other member (D-10), and the extension name allocated collision-free. Users keep the SDK type and get typed access to their additions. A member Dart cannot express this way (call, construct or index signatures, statics) gets a counted diagnostic. Augmentations from several files follow HD-06's ownership (one extension, owned by the first declaring file). A lib type with **no** SDK mapping is not covered here: it follows HD-06 and the implementer reports what happens. Proof is runtime (D-14): the dart2js probe reads, writes and calls an augmented member. | 2026-11-06 | HD-06, D-09, D-10, D-14, D-22 |
